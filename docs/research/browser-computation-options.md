# Browser computation options for LUT Builder

Research date: 2026-10-18

Scope: the first research slice of [issue #9](https://github.com/Today20092/lut_builder/issues/9): run LUT generation in a static browser app, assess TypeScript and Effect 4, and audit local still/video verification. This note recommends an implementation direction; it does not change application code or claim numerical parity has been demonstrated.

## Recommendation

Keep the existing React/TypeScript editor and implement the LUT engine as a small TypeScript port, run in a dedicated Web Worker. It needs no runtime service, Python interpreter, or computation dependency. Reuse the frontend's setup and validation types where their semantics match; keep the Python engine as the reference oracle. Keep all profile/target constants explicit and testable rather than assuming Python's `colour` catalog is automatically available in JavaScript. The project already builds browser assets with Vite and TypeScript (`frontend/package.json`, `frontend/tsconfig*.json`); GitHub Pages only serves the static application, as issue #9 states.

Use the worker for generation, chunked progress, and cancellation messages so the editor stays responsive. Transfer the result's `ArrayBuffer` back to the page rather than copying a large table; transfer detaches the sender's buffer, so the worker should transfer only completed output. These are standard browser APIs ([TypeScript DOM and web-worker compiler guidance](https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options), [MDN Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers), [MDN transferable objects](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects)).

## Runtime options

| Option | Fit for this ticket |
| --- | --- |
| TypeScript in the main thread | Smallest baseline, but generation can monopolize UI work. Use only if representative desktop and phone measurements show it stays responsive. |
| TypeScript in a Web Worker | **Recommended.** Keeps the existing language and build. A worker handles CPU work and can report progress or receive cancellation between bounded chunks; no DOM access is needed for the math. |
| Python through Pyodide/WebAssembly in a worker | Viable prototype/fallback if porting proves too risky. Pyodide provides CPython and NumPy in browsers, but the runtime and packages must be downloaded, initialized, and loaded; its docs warn that long computations on the main thread can freeze the UI. Test whether the exact `colour` version and dependencies used by the project are available and fast enough before selecting this route ([Pyodide browser use](https://pyodide.org/en/stable/usage/index.html), [Pyodide package catalog](https://pyodide.org/en/stable/usage/packages-in-pyodide.html)). |
| WebGPU/custom WASM kernel | Not justified for a 3D LUT port before profiling. It adds a second implementation/runtime path and does not solve profile-data parity or artifact verification. |

Effect 4 is now a stable release: the official release announcement dates 4.0 to September 30, 2026, describes it as a dependency-free core and announces an LTS policy; its repository identifies 4.x as LTS and requires TypeScript 5.9+ with strict checking ([Effect 4.0 announcement](https://effect.website/blog/releases/effect/40), [Effect repository requirements](https://github.com/Effect-TS/effect), [releases](https://github.com/Effect-TS/effect/releases)). It offers typed errors, structured concurrency, cancellation, and resource management, but it does not supply worker execution or LUT/color math. Those needs are met by a small worker message protocol and the existing app stack. Do not add Effect for this port unless the implementation grows enough concurrent tasks or resource lifecycles to justify a new runtime dependency. That is a fit assessment, not a claim that Effect is incompatible with browsers.

No bundle-size, startup, peak-memory, or speed benchmark was run for either route in this research pass. Issue #9 requires those measurements on representative desktop and phone browsers before setting support limits; Pyodide in particular should be compared using the actual packaged runtime plus required wheels, not a generic download-size estimate.

## Porting and numerical parity

The engine's order and edge behavior are part of the product contract, not interchangeable implementation details. The current Python path in [`engine.py`](../../src/lut_builder/engine.py) builds the requested cube lattice; applies the selected camera log decoder; computes source-gamut linear-light CIE Y and `log2(max(Y, 1e-6) / 0.18)` stops; transforms linear RGB to the target gamut; optionally derives monochrome from target-linear Y; applies the selected OETF or log encoder; computes IRE from encoded target-gamut luma when requested; applies bands in declared order (last overlap wins), then low/high encoded-signal warnings (high wins); converts authored sRGB overlay colors for non-709 targets; applies legal-range scaling after overlays; clips and casts the final table to float32; and delegates `.cube` serialization. [`map_exposure`](../../src/lut_builder/setup.py) defines inclusive band edges, fill-zone boundary ties, and warning priority. The profile catalog in [`data.py`](../../src/lut_builder/data.py) validates supported decoder, encoder, and gamut keys against `colour`.

Port those operations in the same order, including data and serialization conventions. Do not replace source-gamut Y with Rec.709 coefficients, move warning/range steps, or use screenshots as proof. The output array's final float32 cast and `.cube` lattice ordering/header must match the export contract. A mathematically similar formula can still diverge at band ties, gamut excursions, or serialized samples.

JavaScript `Number` and ordinary Python floats both use IEEE 754 binary64 on normal supported platforms ([MDN Number](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number), [Python floating-point guide](https://docs.python.org/3/tutorial/floatingpoint.html)); this is a suitable basis for porting the Python/NumPy float64 calculations. It does not guarantee bit-identical results for transcendental functions or different summation paths. Define tolerance at the final float32 LUT values, and separately require exact agreement for discrete choices: selected profile/target, masks, fill zones, warning precedence, channel order, dimensions, and serialization structure.

Before replacing the engine, add independent reference fixtures and compare every supported profile/target and 17/33/65 lattice sizes. Include neutral and colored samples, curve/matrix outputs, stop and IRE bands at both edges and exact ties, fill and overlap behavior, warning priority, out-of-gamut values, full/legal range, float32 final values, and parsed `.cube` domain/order. Exercise progress/cancellation and generation failure without losing the edited setup. Use the existing Python engine to create expected data, plus independently sourced camera/target landmarks so a shared mistake in the Python implementation cannot bless the port. Record measured time and peak memory on representative desktop and phone browsers before setting support/resource limits, as issue #9 requires.

## Local backend feature audit

GitHub Pages cannot serve the current Python backend. The browser migration must not leave the existing local-server buttons as dead calls; issue #9 requires an explicit feature/support matrix and linked follow-ups for unsupported features.

| Capability | What can be accurate in-browser | Boundary / follow-up |
| --- | --- | --- |
| LUT generation, setup import/export, presets, `.cube` download | Entire workflow can be local and accurate after engine parity checks; browser storage is local to the origin and should have JSON backup/export. | Core scope of #9. Keep the exported setup as the portable backup; do not imply cross-device sync. |
| LUT preview | An illustrative editor preview may help tune bands if labeled as illustrative. A trustworthy result preview must apply the **same serialized exported cube** and disclose its interpolation/view policy. | A demonstration still/video frame is not verification. Never label it as verified output. |
| Still verification | A browser verifier can be accurate if it accepts a precisely defined camera-code input, preserves its samples and precision, applies the downloaded/serialized cube with the declared tetrahedral interpolation, and emits the existing SDR view/provenance. The current accepted narrow still contract is untagged, non-interlaced 16-bit RGB PNG or float32 RGB PFM, max 4,194,304 pixels and 48 MiB plus header; transfer/gamut/range must be confirmed. | Current PNG decode invokes FFmpeg to preserve 16-bit RGB. Browser canvas decoding is not an equivalent verified path for that contract. PFM parsing is a plausible smaller first follow-up; any PNG path needs a decoder validated against fixtures. Preserve rejection of color-tagged/graded images, unsupported formats, and unknown interpretation. See [`still-verification.md`](../still-verification.md), [`verification.py`](../../src/lut_builder/verification.py). |
| Video frame verification | In principle, a browser decoder can verify a frame only when native sample precision, stream/frame metadata, matrix, range, chroma location, and reconstruction are explicitly resolved and confirmed before applying the exact exported cube. | Current verification depends on FFmpeg plus FFprobe: supported containers/codecs are restricted; current probe rejects unknown/unsupported metadata and limits video to even dimensions up to 1920×1080. FFmpeg extracts native planar frames and `zscale` converts confirmed matrix/range/chroma to float32 RGB with explicit bilinear chroma reconstruction. Browser playback or a canvas screenshot does not prove equivalent camera RGB. Keep this as a separate follow-up with decoder parity and resource-bound work, or clearly mark unsupported. See [`video.py`](../../src/lut_builder/video.py), [`video-verification.md`](../testing/video-verification.md), [`video-frames.md`](../testing/video-frames.md). |

The existing local verifier applies the serialized `.cube`, tetrahedral interpolation, and SDR rendering in [`verify_rgb`](../../src/lut_builder/verification.py); it reports provenance and clamps only at the cube boundary. Its demo/preview decode is not a verification input. Preserve that distinction in the browser UI and feature matrix. A browser-only generation milestone may ship before camera still/video verification only if the unsupported states are explicit, local calls are removed or disabled with explanation, and the required follow-up issues are linked.
