# Video-frame selection for LUT verification

Research date: 2026-09-06. Resolves [Choose reliable video-frame extraction and source-color identification](https://github.com/Today20092/lut_builder/issues/30). Recommendations below are a proposed implementation contract, not implemented or tested product support.

## Recommendation

Use the existing local backend to run FFprobe and FFmpeg. Select one decoded frame; keep its high-precision samples on the backend for LUT evaluation. Send only a display-ready image to the browser. A file chooser, time control, previous/next frame buttons, and explicit source interpretation are sufficient; playback is unnecessary.

The extraction is straightforward. Preserving the meaning of the samples is the part that needs validation: codec, YCbCr matrix, signal range, camera gamma, and camera gamut are distinct properties. Sony explicitly requires a LUT input matching the recorded S-Log3/S-Gamut3 or S-Gamut3.Cine material. A codec or camera model alone does not establish that match. [Sony LUT guidance](https://helpguide.sony.net/di/pp/v1/en/contents/TP1000756721.html)

## Selecting a frame precisely

Define the UI time as elapsed presentation time from the selected video stream's first decoded frame. For a requested time, select the first frame at or after it; show its actual time. Keep integer presentation timestamps and the rational time base internally. Previous/next means adjacent decoded frames, not adding or subtracting `1 / average_fps`. This is a proposed, deterministic UX contract for variable-frame-rate input.

FFmpeg's `select` filter exposes decoded frame ordinal `n`, timestamp `pts`, and seconds `t`; `setpts=PTS-STARTPTS` can normalize the timeline. An initial implementation can decode from the beginning, normalize timestamps, select the first qualifying frame, and stop after one output frame. Selecting a known ordinal from the beginning also provides an unambiguous reference path. Avoid an `fps` filter, output `-r`, or other frame-rate conversion; `-fps_mode passthrough` avoids synchronization-driven duplication or dropping. [FFmpeg select/setpts/fps filters](https://ffmpeg.org/ffmpeg-filters.html#select_002c-aselect), [FFmpeg synchronization options](https://ffmpeg.org/ffmpeg.html#Advanced-options)

This simple path becomes slow near the end of long clips. Optimize only after measuring: seek to an earlier keyframe, decode forward, then select by the original timestamp and verify the selected frame against the reference path. Input `-ss` normally seeks to an earlier seek point and, with default accurate seeking during transcoding, decodes and discards the intervening material. Its default position includes the file start offset; `-seek_timestamp` changes that convention. Do not mix file-relative seek values with normalized stream time without an explicit offset. [FFmpeg seeking](https://ffmpeg.org/ffmpeg.html#Main-options), [seek_timestamp](https://ffmpeg.org/ffmpeg.html#Advanced-options)

FFprobe `-show_frames` provides per-frame information; `-read_intervals` seeks approximately, so its first returned frame is not proof of an exact requested position. Avoid a mandatory whole-file scan merely to open the picker. Reject missing/nonmonotonic presentation timing for timestamp selection initially, or offer a clearly labeled decoded-frame-number fallback. Timecode metadata is a separate recording label, not elapsed seconds. [FFprobe frame/interval options and timecode](https://ffmpeg.org/ffprobe.html)

## Color and precision contract

1. Probe the selected stream and decoded frame: codec/profile, dimensions, pixel format/component depth, chroma subsampling/location, range, matrix, transfer, primaries, rotation, and sample aspect ratio. Retain frame-level values where available and disclose conflicts with stream-level metadata. FFprobe reports stream/container tags and frame details; FFmpeg represents range, transfer, matrix and primaries separately. [FFprobe](https://ffmpeg.org/ffprobe.html), [FFmpeg pixel/color definitions](https://ffmpeg.org/doxygen/trunk/pixfmt_8h.html)
2. Decode at source precision. Convert YCbCr to encoded RGB using the confirmed matrix, range and chroma location. Explicitly configure these inputs rather than silently accepting defaults. Do not apply a log-to-display transform, tone mapping, automatic contrast, or a gamut conversion before the LUT input stage. FFmpeg `zscale` exposes matrix/range/chroma input controls independently of transfer and primaries. Its transfer/primaries defaults preserve the input; proprietary camera log decoding should remain in the LUT pipeline. [zscale options](https://ffmpeg.org/ffmpeg-filters.html#zscale-1)
3. Prefer planar float RGB as the internal extraction output, retaining a descriptor for plane order, byte order, dimensions and source interpretation. Do not claim this restores missing source precision or reverses chroma subsampling. Test that the chosen conversion preserves superblack/superwhite and negative/out-of-range RGB until the LUT's explicit input-domain policy is applied; silently clamping at frame export would invalidate that check. FFmpeg defines float RGB pixel formats, but an installed format is not evidence that an entire filter chain is correct. [FFmpeg pixel formats](https://ffmpeg.org/doxygen/trunk/pixfmt_8h.html)
4. Apply the generated LUT with a specified interpolation method, then perform the explicit output-to-display conversion. Retain numerical results separately from the display image. Label an untreated log view “Source signal”; a view with a viewing transform should name that transform. “LUT off” alone cannot distinguish these meanings. This is the recommended product contract.

A 16-bit PNG can preserve integer RGB precision better than an 8-bit intermediate, but its bounded unsigned samples cannot preserve every floating-point excursion. PNG also carries color interpretation through profile/gamma/color-space chunks. Default canvas image data is an 8-bit path and canvas drawing can convert color spaces; a 16-bit file does not make a browser canvas a camera-sample verification buffer. Use an explicitly tagged display image after processing, with numerical verification on backend samples. Higher-precision browser APIs would require a separately validated path. [PNG sample depths and color metadata](https://www.w3.org/TR/png-3/#11IHDR), [PNG color values](https://www.w3.org/TR/png-3/#6Colour-values), [HTML canvas pixel manipulation](https://html.spec.whatwg.org/multipage/canvas.html#pixel-manipulation), [canvas color conversion](https://html.spec.whatwg.org/multipage/canvas.html#colour-spaces-and-colour-correction)

## Metadata-assisted interpretation

Show two groups: **Reported by file** and **Use for this preview**. The second contains editable camera gamma/gamut plus advanced matrix/range/chroma controls. Include provenance such as “File reports BT.709 matrix” or “Suggested from camera tag; confirm.” Record the confirmed settings with the selected frame.

Video identification is container/stream metadata and codec signaling, not simply photo EXIF. FFmpeg's standard transfer enumeration includes generic logarithmic values, which must not be relabeled Sony S-Log3 or Panasonic V-Log. Neither a BT.709 matrix tag nor a codec/profile proves the camera's RGB gamut or gamma. Manufacturer-specific tags may support a suggestion only after a documented mapping and sample-file check; this investigation establishes no universal automatic camera-profile detector. [FFprobe metadata](https://ffmpeg.org/ffprobe.html), [FFmpeg transfer/primaries enums](https://ffmpeg.org/doxygen/trunk/pixfmt_8h.html), [Sony separate Gamma/Color Mode settings](https://helpguide.sony.net/di/pp/v1/en/contents/TP0000909109.html)

Require the user to confirm gamma/gamut and resolve missing or conflicting conversion properties before calling the mode camera-matched verification. Display codec, container, subsampling and bit depth as read-only facts; users should not need to re-enter a recording format that the decoder already identifies. They can specify the camera recording profile when metadata is insufficient.

## Initial scope and failure behavior

Recommended first acceptance target: local MP4/MOV, progressive H.264 or HEVC at 8/10 bit, and conventional 10-bit ProRes 422. Select the main video stream explicitly; exclude attached cover art. Support VFR using presentation timestamps. Gate actual support on a successful probe, selected-frame decode and tested color interpretation, not filename extension.

Defer RAW, encrypted media, interlacing, image-sequence containers, dynamic HDR/Dolby Vision processing, and automatic camera-profile detection. Do not advertise every codec compiled into FFmpeg. Handle rotation/sample aspect ratio for display explicitly; retain the coordinate mapping for any pixel inspection. These are proposed support boundaries, not claims that those formats are inherently unsupported by FFmpeg.

If either executable, the required decoder, or `zscale` is unavailable, disable video import with the specific missing capability and keep image/demo modes available. Do not install tools silently. Run argument arrays without a shell, accept only the application's local uploaded-file handle, restrict protocols, cap dimensions/output allocation, allow cancellation, and delete temporary media when the session ends. Return useful probe/decode errors without exposing unrelated paths. These are implementation recommendations for handling an untrusted media file.

## Small verification gate and remaining choices

Before release, use one small fixture set covering: VFR with nonzero initial PTS and B-frames; known limited/full-range 10-bit neutral/color patches including excursions; missing/conflicting tags; and a supported camera-log frame. Assert selected frame identity against sequential decode, range/matrix conversion numerically, and preview LUT results against the same exported cube and declared interpolation. Confirm the browser receives only display pixels, and check a wrong-profile selection is clearly visible in the interpretation UI. A display screenshot alone cannot establish mathematical correctness.

Product defaults proposed for the map: first frame at/after requested elapsed time; manual confirmation of source interpretation; sRGB display preview; video import available when local tool capability checks pass. Remaining choices are clip size/duration limits and cancellation UX, whether to package FFmpeg later, and whether exact-frame navigation merits indexing long clips. No playback or general-purpose media library is needed for the first version.
